# Benchmark — Muse-Glimmer-30B on W7900 (gfx1100)

> Reproduce: `scripts/w7900-repro/` (two methods — Docker image or bare metal).
> Metric definitions, prompt set, and sampling: [`METHODOLOGY.md`](METHODOLOGY.md).
> All numbers below are pulled verbatim from the per-cell JSONs.

This is the **Radeon PRO W7900 (gfx1100 / RDNA3)** validation of **Study 2 —
throughput under load**, the original throughput-under-load study first measured
on the gfx1151 APU (see [`benchmark.md`](benchmark.md#study-2--throughput-under-load-temp-10--original-study)).
Same llama.cpp arch, same GGUF weights, same Study-2 sampling and prompt corpus;
only the GPU changes. `c` is llama.cpp concurrency (`-np`).

## Environment manifest

| Item | Value |
|---|---|
| GPU | AMD Radeon PRO **W7900**, `gfx1100` (RDNA3), 96 CUs, **48 GiB GDDR6** |
| ROCm | 7.2.4 (llama.cpp runtime image base) |
| Kernel | 6.8.0-134-generic |
| llama.cpp | prebuilt gfx1100 HIP build (`llama-server`) shipped in the ACR image `muse-glimmer-llamacpp_2026_08_12`; `--version` reports `0 (unknown)` |
| GGUF | `meta-models/Muse-Glimmer-30B-GGUF` — `…-kquant-17gb.gguf` (15.6 GiB) / `…-kquant-dynamic.gguf` (18.3 GiB) + `dflash-kquant.gguf` drafter |
| Sampling | `temp=1.0 top_p=0.95 top_k=64 seed=42`, `reasoning_strength=high`, `max_tokens=512`, per-slot ctx 8192, **5 reps** |
| Isolation | single card, `HIP_VISIBLE_DEVICES=0`, `--device=/dev/kfd --device=/dev/dri` |

> **`rocm-smi` VRAM on W7900 is a real dedicated-VRAM measurement** — unlike the
> Strix Halo unified-memory caveat in [`benchmark.md`](benchmark.md#caveats), the
> W7900 has dedicated GDDR6, so the VRAM column below is the true resident-DRAM figure.

## Headline

| Weight | c=1 baseline / DFlash | c=4 baseline / DFlash | c=16 baseline | c=32 baseline |
|---|---:|---:|---:|---:|
| 17GB | 33.72 / 56.35 tok/s | 66.46 / 77.44 tok/s | 218.56 tok/s | 293.29 tok/s |
| dynamic | 30.61 / 51.92 tok/s | 65.63 / 71.51 tok/s | 209.65 tok/s | 265.71 tok/s |

DFlash is reported at `c=1` and `c=4` only — it is a single-stream / light-concurrency
optimization. At `c ≥ 8` leave DFlash **off**: its advantage has already shrunk to
`+9–17 %` by `c=4` and the baseline is the throughput winner at `c=16` / `c=32`.

## Concurrency scaling (baseline agg tok/s)

| c (=`-np`) | 1 | 4 | 16 | 32 |
|---|---:|---:|---:|---:|
| **17GB** baseline | 33.72 | 66.46 | 218.56 | 293.29 |
| **dynamic** baseline | 30.61 | 65.63 | 209.65 | 265.71 |
| VRAM 17GB / dynamic (GiB) | 15.8 / 18.5 | 16.7 / 19.4 | 19.1 / 21.8 | 22.2 / 24.9 |

Both weights scale up with concurrency but **clearly saturate**: `c=16 → c=32`
adds only **+34 % (17GB) / +27 % (dynamic)**. Peak VRAM stays **≤ 24.9 GiB** of 48
(dynamic `c=32`) — roughly half the card free at maximum load. (`c=32` needs
`-c 262144` > the 131072 training context; harmless, since each request is < 1k tokens.)

## Study 2 — throughput under load (full detail, 12 cells)

| weight | np | mode | agg tok/s | TTFT p90 (s) | TPOT med (s) | VRAM (GiB) | acceptance |
|---|---:|---:|---:|---:|---:|---:|---:|
| 17gb | 1 | baseline | 33.72 | 0.224 | 0.0293 | 15.8 | — |
| 17gb | 1 | DFlash | 56.35 | 0.233 | 0.0167 | 18.0 | 0.196 |
| 17gb | 4 | baseline | 66.46 | 0.421 | 0.0590 | 16.7 | — |
| 17gb | 4 | DFlash | 77.44 | 0.562 | 0.0493 | 19.0 | 0.194 |
| 17gb | 16 | baseline | 218.56 | 1.424 | 0.0587 | 19.1 | — |
| 17gb | 32 | baseline | 293.29 | 2.380 | 0.0899 | 22.2 | — |
| dynamic | 1 | baseline | 30.61 | 0.240 | 0.0323 | 18.5 | — |
| dynamic | 1 | DFlash | 51.92 | 0.244 | 0.0202 | 20.7 | 0.203 |
| dynamic | 4 | baseline | 65.63 | 0.430 | 0.0595 | 19.4 | — |
| dynamic | 4 | DFlash | 71.51 | 0.576 | 0.0530 | 21.7 | 0.201 |
| dynamic | 16 | baseline | 209.65 | 1.463 | 0.0656 | 21.8 | — |
| dynamic | 32 | baseline | 265.71 | 2.290 | 0.0951 | 24.9 | — |

**Reading the table:**

- **Concurrency scaling & saturation.** Baseline scales `33.7 → 66.5 → 218.6 → 293.3`
  (17GB) and `30.6 → 65.6 → 209.7 → 265.7` (dynamic) across `c = 1 → 4 → 16 → 32`
  (~8.7× end-to-end), but `c=16 → c=32` only adds +34 % / +27 % — the GPU is near
  compute saturation there.
- **DFlash helps at low concurrency, fades as it rises.** Aggregate speedup is
  **+67 % (17GB) / +70 % (dynamic)** at `c=1`, down to **+17 % / +9 %** at `c=4`.
  DFlash lowers per-token time (TPOT) with draft acceptance ~19–20 % at `c ≤ 4`
  (temp 1.0). By `c ≥ 8` the baseline wins, so DFlash is not reported past `c=4`.
- **dynamic vs 17GB.** The dynamic weight runs ~5–10 % slower and uses ~2–3 GiB more
  VRAM across the board.
- **Aggregate vs per-request.** `agg tok/s` (Σ tokens ÷ max per-request wall) answers
  "how many tokens/s can this server push"; per-request TPOT and TTFT p90 rise with
  concurrency (queueing).

## W7900 vs gfx1151 (reference)

Aligned cells against the gfx1151 Study-2 record in [`benchmark.md`](benchmark.md#study-2--throughput-under-load-temp-10--original-study):

| cell | gfx1151 (ref) | W7900 | ratio |
|---|---:|---:|---:|
| 17GB c=1 baseline | 10.52 | 33.72 | 3.2× |
| 17GB c=1 DFlash | 22.26 | 56.35 | 2.5× |
| 17GB c=4 baseline | 15.60 | 66.46 | 4.3× |
| 17GB c=4 DFlash | 27.30 | 77.44 | 2.8× |
| 17GB c=16 baseline | 34.47 | 218.56 | 6.3× |
| dynamic c=1 baseline | 9.09 | 30.61 | 3.4× |
| dynamic c=4 baseline | 20.90 | 65.63 | 3.1× |
| dynamic c=16 baseline | 31.05 | 209.65 | 6.8× |

The W7900 (RDNA3 desktop card, dedicated GDDR6) is roughly **3.2–3.4× at `c=1`,
2.5–4.3× at `c=4`, and 6.3–6.8× at `c=16`** faster than gfx1151 (Ryzen AI APU,
~215 GB/s unified LPDDR5X). The gap widens with concurrency — the desktop card's
memory bandwidth and compute pull further ahead as the batch grows.

## Recommended serving configurations (W7900)

Two W7900-tuned `llama-server` presets, grounded in the measurements above
(throughput saturates near `c=16`; DFlash helps only at low concurrency; the
48 GiB card has VRAM headroom). `-c` is the **total** context and is split
across slots, so per-slot context = `-c / -np`.

### 1. High throughput — many concurrent users

`-np 16` with **64K tokens per slot** — the measured throughput sweet spot
(`c=16` ≈ 218 tok/s aggregate on the 17GB weight). Keep DFlash **off**: it is
counter-productive once `c ≥ 8`.

```bash
llama-server -m models/muse-glimmer-30B-kquant-17gb.gguf \
  -a muse-glimmer-30B -ngl 99 -fa on --host 0.0.0.0 --port 8080 --jinja \
  -np 16 -c 1048576            # 16 slots × 65536 tokens/slot
```

### 2. Long context — single request at the full 128K window

`-np 1` (or `2`) with the model's **full 131072-token** context — for one long
document or conversation. At `-np 1`, turn DFlash **on**: single-stream
speculative decoding is ~1.9–2.2× faster with byte-identical greedy output.

```bash
llama-server -m models/muse-glimmer-30B-kquant-17gb.gguf \
  -a muse-glimmer-30B -ngl 99 -fa on --host 0.0.0.0 --port 8080 --jinja \
  -np 1 -c 131072 \
  -md models/dflash-kquant.gguf -ngld 99 --spec-type draft-dflash --spec-draft-n-max 16
# two full-128K streams instead: -np 2 -c 262144  (drop the DFlash flags)
```

> Both presets are sized for the 48 GiB card: the high-throughput preset trades
> per-slot length for aggregate token rate, the long-context preset does the
> opposite. Swap in `…-kquant-dynamic.gguf` for the dynamic weight (~5–10 % slower,
> ~2–3 GiB more VRAM). With a launcher these map to `NP` / `CTX_PER_SLOT`
> (total `-c = NP × CTX_PER_SLOT`) and `USE_DFLASH`.
>
> **Measured on the W7900** (`-fa on`, ROCm 7.2.4 submission host): high-throughput `-np 16 -c 1048576` ≈ **30 GiB**
> (17GB) / **33 GiB** (dynamic); long-context `-np 2 -c 262144` ≈ **22 GiB** — both
> fit 48 GiB with margin. llama.cpp pads each slot to a multiple of 256, so use round sizes
> (`16×65536=1048576`, `2×131072=262144`); a bare `65535` per slot rounds up to `65536`.
